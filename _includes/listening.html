Source is _data/site_songs.csv: title, artist, header row as keys. THE FILE'S ORDER IS LOAD-BEARING AND IT IS NOT THE EXPORT'S. Apple Music writes the list sorted, and that order is the exporter's rather than any fact about listening -- so a positional selection over it renders an alphabetical run, and the run says something false. Measured 2026-09-08 before the repair: the first twenty rows ran Adona to Depeche Mode, so a sign-off drawing its single track from a group-count modulus could never have shown anything outside that window. The committed file is therefore shuffled once, deterministically, and a re-export must be shuffled again before it lands. The operation, seed included, so it is repeatable: python3 -c "import csv,random;p='_data/site_songs.csv';r=list(csv.reader(open(p,encoding='utf-8')));h,b=r[0],r[1:];random.Random(20260908).shuffle(b);f=open(p,'w',encoding='utf-8',newline='');w=csv.writer(f,quoting=csv.QUOTE_ALL);w.writerow(h);w.writerows(b)" The failure mode is visible rather than silent: an alphabetical file makes an alphabetically ordered widget, which is the symptom that found this. Selection is by day of year and not at random, following tagline.html: a build must be reproducible, and `sample` would make two builds of one commit differ. The Actions cycle rebuilds daily (RULED 2026-08-18), so the rotation runs on that cadence. `start` is taken modulo the row count and not the group count, which is the whole of the repair: the first track can land on any row, so the sign-off's single track is drawn from the entire list and walks all of it across a cycle.
